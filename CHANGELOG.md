# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- `updater.sh` follows channels, withdrawn releases, a pin and signed tags. With `channel=rc` in its settings it also follows `vX.Y.ZrcN` tags (`rc1` < `rc2` < `rc10` < the release, the same order as `selfupdate.tag_key` and `git -c versionsort.suffix=rc`); `stable` (the default, and what anything else means) ignores candidates. A release is withdrawn with an annotated tag `retired/vX.Y.Z` whose message is the reason (no file to edit): a retired tag is never a target, and a device that runs a retired version goes to the best valid one even if it is lower. `pin=vX.Y.Z` makes that tag the target whatever the channel, the running version or a retirement, with the same differential verdict as any update, and the state key `pin_retired` and the log say when the pinned tag is retired. When the `warpzone/data/allowed_signers` of the version the device runs lists a key (`WZ_ALLOWED_SIGNERS` for tests), a release, a candidate, a pin and a retirement must be an annotated tag with a single SSH signature that `git verify-tag` accepts against it, checked with the OpenPGP and X.509 verifiers switched off and without the user's git configuration, so a tag signed some other way cannot get past it; a release cannot change the keys that check it, and the signature must be for a tag of that very name (a signed `v0.2.0` published as `v0.3.0` is refused). A retirement tag must sit on the commit of the release it names, and at most the newest 50 `retired/` tags are looked at per tick. Once a version with keys has been trusted, signatures stay required, with the last keys kept in the state folder, even after a pin or a retirement takes the device to a release without the file. With no key nothing is required and the log says so. The file ships with comments only. What was chosen at one tick (a version being tried, one under a second look) is checked again at the next: if it was retired, is off the channel or is no longer signed it is dropped. `updater.sh order` prints how it reads a list of tags. [docs/releasing.md](docs/releasing.md) explains how to sign a tag, publish a candidate and retire a release. Still not installed or started by anything. See [docs/self-update.md](docs/self-update.md#the-updater-script) and [docs/design.md](docs/design.md#autonomous-updates-contract).
- `warpzone/data/updater.sh`, the POSIX `sh` core of the autonomous update (shipped as package data, not installed or started by anything yet, so `warpzone self-update` and its timer are unchanged). `updater.sh tick` takes a lock, honours `enabled`, defers for at most 72 hours while the frontend is running, fetches at most once a day, picks the highest `vX.Y.Z` tag that is newer, an ancestor of `origin/main` and whose `__version__` matches, checks it out and verifies it in three steps with a time limit (warpzone imports and `--version` equals the tag, `provision device --unattended`, `warpzone health`). When a check fails it goes back to the previous version and runs the same check: if that passes the tag is marked bad (`bad/<tag>`) and never tried again; if it fails too the environment is at fault, the tag is not blamed and the device waits 1, 2, 4 and then 7 days. A power cut or a kill halfway does not burn the tag (two attempts without a verdict, then back and one day's wait), a new release is checked again after the next boot, and the state is a `key=value` file written by the script only, read line by line and never sourced. A checkout on a release tag or on a clean branch inside `origin/main` is managed; one with commits of its own, a loose commit or local changes is left alone (no `reset`, `stash` or `clean`). A stale `.git/index.lock` is removed. `menu` and `selftest` subcommands. A step that is cut off takes its whole process group with it, the tick has a 25 minute budget (running out of it is an environment failure, not a bad release), a release that fails is checked once more before it is marked bad, a checkout that an update left half done is finished again, and `--no-overwrite-ignore` protects the user's ignored files. Installation and the timer units come later. See [docs/self-update.md](docs/self-update.md#the-updater-script) and [docs/design.md](docs/design.md#autonomous-updates-contract).
- Two optional keys under `[devices.<name>]`: `channel` (`"stable"`, the default, or `"rc"`) and `pin` (a tag, `vX.Y.Z` or `vX.Y.ZrcN`), validated when the config is loaded and documented in `examples/config.example.toml`. They do not change what `warpzone self-update` does yet. Release candidates now order correctly (`v0.3.0rc1` < `v0.3.0rc2` < `v0.3.0`), and [docs/design.md](docs/design.md#autonomous-updates-contract) describes how a device will keep itself on a working release, marking what is not implemented.
- `warpzone provision device <name> --unattended`, for a run nobody watches. It never puts the bootstrap ignores on a folder Syncthing already has (it uses the final ones when the whitelist files are on disk and otherwise leaves the folder alone, with a warning), refuses to change the `type`, the `versioning` or the path of an existing folder, stops before any change when an existing folder has no marker (a card that is not mounted), skips with a warning a new folder that the hub does not have yet instead of failing, turns a new folder whose whitelists do not arrive (30 s by default) into a warning, and only warns about the SyncThingy flatpak grant instead of making it. It exits `3` when a write was held back because ES-DE, an emulator or a file ES-DE rewrites is open, `0` when it finished and any other value on failure. Without `--unattended` nothing changes. See [docs/self-update.md](docs/self-update.md#unattended-provisioning) and [docs/design.md](docs/design.md#autonomous-updates-contract).
- `warpzone health [device]`, the check that a version of warpzone works on a device, and the third step of verifying an update. It loads the config and the profiles, runs as dry runs `settings apply`, `play-state sync`, `links sync` and `frontend refresh` (the ones that apply to the device) and fails any that raises, exits non-zero or takes longer than the 15 seconds ES-DE gives its startup scripts, and checks that the ES-DE startup scripts and the systemd units exist and run an interpreter that imports warpzone. Services and timers are skipped where there is no systemd user manager. It writes no user data, needs no DATs or optional tools, and does not prove that a game starts or that Syncthing syncs. It exits `0` when everything works and `1` when a check failed. `play-state sync --dry-run` no longer creates its lock file. See [docs/self-update.md](docs/self-update.md#checking-a-version) and [docs/design.md](docs/design.md#warpzone-health).
- `warpzone self-update`, run on a device: fetches the tags of the git clone warpzone runs from and checks out the newest `vX.Y.Z` tag when it is newer than the running version. It never downgrades, refuses a clone with local changes, says so and exits cleanly when warpzone is not a git checkout, and exits `0` with a short message when the remote cannot be reached. `--dry-run` only reports. It logs to `~/.local/state/warpzone/self-update.log`, and reinstalls the editable package only when `pyproject.toml` changed (an editable install reports the new `warpzone --version` by itself). See [docs/self-update.md](docs/self-update.md).
- `provision device` installs and enables a systemd user timer (`warpzone-self-update.timer`: daily, `Persistent=true`, and five minutes after boot) that runs `warpzone self-update`, for every profile and independent of ES-DE. It is idempotent and honours `--dry-run`. `warpzone doctor` warns when a device does not have it. A device turns it off with `self_update = false` in its `[devices.<name>]` table. See [docs/self-update.md](docs/self-update.md).
- The end-to-end test also starts from an empty hub (no whitelist, ROM or BIOS in its folders), adds the whitelists while `provision hub` waits for them, and checks the created folders, the final ignores and that a device receives a whitelisted game.
- A second shipped profile, `anbernic-rg351mp`, for an Anbernic RG351MP running dArkOS with its games on an exFAT card. The library goes in `/roms/library`; the folders of the device ignore permissions (`ignore_perms` in a profile sets Syncthing's `ignorePerms`); and `provision device` writes `~/.emulationstation/es_systems.cfg` as a copy of the OS's system list with the ROM folders moved into the library, and points both RetroArch configs at the library's BIOS folder and at the save and state folders that sync (the same hub folders as the Steam Deck). Both files are written only while EmulationStation or RetroArch is closed, backed up before an edit, and left unchanged by a second run. `warpzone doctor` flags a missing or outdated override and RetroArch keys that are not set. Profiles gain the tables `[es_systems]` and `[retroarch]`, and a save entry may set `create_when`. See [docs/anbernic.md](docs/anbernic.md).
- Scraped artwork and descriptions for a frontend that is not ES-DE. A profile gains an `[artwork]` table (`format`, `kinds`, `systems`, `media`, `metadata`, `gamelists`, optional `refresh`), and `anbernic-rg351mp` uses it: a device that lists `frontend` receives the hub's `wz-media` and `wz-esde` receive-only, limited to the covers and the gamelists of the systems that have a folder in its library, and `provision device` converts the ES-DE gamelists into EmulationStation's own, with absolute `<image>` paths to the covers that exist, only for games that are on the device, under the name the system list gives each system (`[es_systems.rename]` honoured; `pokemini` becomes `pokemonmini`, `psp` becomes `ppsspp`). The converter is picked by the format name, so another frontend is one more small converter. Favourites, play counts and last played times that the frontend saved are kept. New `warpzone frontend refresh` widens the scope and rewrites the gamelists, only while the frontend is closed, and `provision device` installs a `systemd --user` timer that runs it. `warpzone doctor` reports missing or stale gamelists and the timer. The hub's folders and the Steam devices are unchanged. See [docs/anbernic.md](docs/anbernic.md#artwork) and [docs/design.md](docs/design.md#frontend-artwork).
- `warpzone inbox` recognises Wii U `.wua` files (Cemu's ZArchive) by the footer at the end of the file, reading only its last 16 bytes, and files them in `library/roms/wiiu/roms/` under their own name, also when they arrive inside a `.zip`, `.7z` or `.rar`. A `.wua` with a wrong or truncated footer goes to review. See [docs/inbox.md](docs/inbox.md).
- `warpzone inbox` recognises PS4 `.pkg` files by the magic `\x7fCNT` and the content id (`XXnnnn-CUSAnnnnn_nn-...`) in the header, also inside an archive, and reports the title id (`CUSA...`). With [`orbis-pkg-util`](https://crates.io/crates/orbis-pkg-util) configured (`[inbox] orbis_pkg_util`, or on PATH; reported in the `tools:` line and by `warpzone doctor`) a base game is extracted in the local work folder, checked (`eboot.bin`, `sce_sys/param.sfo`) and placed as a folder in `library/roms/ps4/games/<CUSAnnnnn>/` through a `.part` copy and a rename, with a `library/roms/ps4/shortcuts/<Title>.desktop` that ES-DE lists and EmuDeck's shadPS4 launcher runs; both whitelist lines are printed. A game already in the library is reported and not touched, and an update or DLC package goes to review (updates are not merged). Without the tool the `.pkg` is filed in `library/roms/ps4/` as before, with a note. A PS3 `.pkg` or a `.pkg` with an unexpected header keeps going to review. See [docs/inbox.md](docs/inbox.md#ps4-games).
- Favourites and play statistics travel between frontends. A device that lists the new `play-state` folder group shares a new two-way folder, `wz-play-state`, with one JSON Lines file per device, keyed by hub system and ROM path, so `wz-esde` and `wz-media` do not change. Removing a favourite sticks (last change wins, with a change time per game), the play count is the sum across gamelists with existing counts absorbed once, and last played is the latest. Devices that share ES-DE's gamelist count as one, so a play is not counted twice. Times are stored in UTC and shown in each device's zone, and a change made after seeing another wins even on a wrong clock. State for a game a device lacks is kept and ignored. ES-DE's gamelists are edited only while it is closed or from a new startup script, which runs before ES-DE reads them, keeping every other byte, with a backup; they gain a small `<warpzonePlayState>` element when they hold plays from elsewhere. New `warpzone play-state sync`, a `warpzone-play-state.timer` (`[play_state] refresh` in a profile), `paths.play_state` in both shipped profiles, and a `Play state` line in `warpzone doctor`. On a frontend that is not ES-DE, `frontend refresh` does it all. To enable it, add `play-state` to `folders`, run `provision hub`, then `provision device` on each device. See [docs/design.md](docs/design.md#play-state) and [docs/anbernic.md](docs/anbernic.md#favourites-and-play-statistics).
- Profiles gain a `[shadps4]` table (`config`, `process`, `install_dirs`), and `steamos-emudeck` declares `{library}/roms/ps4/games`: `provision device` adds that folder to shadPS4's install directories, in `~/.local/share/shadPS4/config.json` (`General.install_dirs`, v0.21 and later) and in `config.toml` (`GUI.installDirs`) when they exist, so the consoles find the PS4 games that `inbox` extracts. Existing entries are kept, the old file is backed up, nothing is written while shadPS4, its Qt launcher or a game runs, a second run changes nothing, and `--dry-run` only reports. `warpzone doctor` flags a console whose config lacks the folder. The settings layer was not used because it writes scalar keys and this is an array derived from each console's own library path. See [docs/emudeck.md](docs/emudeck.md#shadps4-install-directory).
- `provision device` starts PS4 games without EmuDeck's launcher. EmuDeck's `shadps4.sh` runs `Shadps4-qt.AppImage -d -g <eboot>`, and that Qt launcher can crash (exit 139) with those arguments although the emulator runs the same game. A profile that declares `[shadps4.launch]` (`steamos-emudeck` does) gets a small bash script in `~/.local/share/warpzone/shadps4-launch.sh`: it reads the quoted eboot path from the `Exec=` line of the `.desktop` shortcut, the version selected in the Qt launcher (`versionSelected` in `qt_ui.ini`, an AppImage or its folder; the first of `versions.json` when none is usable) and runs its `Shadps4-sdl.AppImage -f true -g <eboot>`. Without any version it prints an error asking to open the shadPS4 launcher once, and exits non-zero. `provision device` then points the `SHADPS4` entry of ES-DE's `custom_systems/es_find_rules.xml` at the script: only that entry changes, the old file is backed up, nothing is written while ES-DE runs, and a second run changes nothing. EmuDeck's own script is never edited. EmuDeck may rewrite the rules file, so `warpzone doctor` warns (`shadPS4 launcher`) when the entry no longer points at the script, or the script is missing, outdated or not executable. See [docs/emudeck.md](docs/emudeck.md#shadps4-launch-script).
- `warpzone inbox` files PS Vita games. A decrypted dump (`eboot.bin` next to `sce_sys/param.sfo`, with a Vita title id `PCS[A-I]nnnnn` and category `gd` or `gdc`) in a folder, or in a `.zip`, `.7z` or `.rar` at its top level or inside one top folder, is copied through a `.part` copy and a rename to `library/roms/psvita/app/<TITLEID>/`, and `library/roms/psvita/<Title>.psvita`, whose content is only the title id, is written for ES-DE and Vita3K; both whitelist lines are printed, also in report mode. A game or a launcher already in the library is reported and never overwritten. Updates, DLC, other categories, title ids that are not Vita ones, dumps that carry `sce_pfs` (Vita3K has to install them), Vitamin dumps (they hold `sce_module/steroid.suprx`, which Vita3K rejects, so they are never placed; the reason suggests a `.pkg` with `work.bin` or a NoNpDrm dump), several games in one item and symbolic links go to review with a reason; `.vpk` and installable `.pkg` files and PS3 folders keep going to review. See [docs/inbox.md](docs/inbox.md#ps-vita-games).
- `warpzone inbox` files the licence of a PS Vita game, which a game installed by Vita3K needs: its `eboot.bin` stays an encrypted SELF, and without `ux0/license/<TITLEID>/<CONTENT_ID>.rif` Vita3K logs "No klic provided for encrypted App" and does not start it. Along with the game, inbox accepts its licence as `sce_sys/package/work.bin` (NoNpDrm) or as a `<CONTENT_ID>.rif` in the item (in `license/<TITLEID>/`, or loose next to the game folder), checks it (512 bytes, a Vita content id at offset 0x10, the same title id as the game and the content id of its `param.sfo`) and files it in `library/roms/psvita/license/<TITLEID>/<CONTENT_ID>.rif` through a `.part` copy that is read back, never over a different file, printing the whitelist line `!/roms/psvita/license/<TITLEID>`. A game whose `eboot.bin` is encrypted (decided as Vita3K does: an `SCE\0` SELF whose first segment is not plain and whose app info says APP, not the magic alone) and has no licence goes to review with that reason, and a dump with `work.bin` but no `sce_pfs` is no longer sent to review for it. `provision device` links `roms/psvita/license/<TITLEID>` into `ux0/license/<TITLEID>` with a second rule, `[links.vita3k-license]`, which makes `ux0/license` when Vita3K has not (the table gains `noun` and `create_target`), and `warpzone doctor` reports `Vita3K license links`. See [docs/inbox.md](docs/inbox.md#ps-vita-games), [docs/emudeck.md](docs/emudeck.md#vita3k-games) and [docs/design.md](docs/design.md#ps-vita-games).
- Profiles gain a `[links.<id>]` table (`source`, `target`, `process`, `match`, `require`) that keeps one symlink per library title inside an emulator's own game folder, and `steamos-emudeck` declares it for Vita3K (`~/Emulation/storage/Vita3K/ux0/app/<TITLEID>` -> `~/Emulation/roms/psvita/app/<TITLEID>`). `provision device`, the new `warpzone links sync <name>` (`--dry-run`, `--quiet`) and a new ES-DE startup script, `warpzone-links.sh`, create the missing links, so a newly whitelisted game appears with no manual step. Only links are changed: a real folder is never touched, only a dangling link into the library folder is removed, nothing happens while Vita3K runs, a second run changes nothing, and a game is linked once `eboot.bin` and `sce_sys/param.sfo` have arrived. The script is bounded and always exits `0`. `warpzone doctor` reports `Vita3K game links` (games without a link, dangling links, a missing startup script). Vita3K needs no cache entry for this according to its public source; running a game through a symbolic link on a console is untested. See [docs/emudeck.md](docs/emudeck.md#vita3k-games) and [docs/design.md](docs/design.md#title-links).
- `warpzone inbox` recognises 3DS images (`.3ds` and `.cci`, loose, in a folder or in an archive) by their NCSD and NCCH headers, reading only the first 0x200 bytes and the NCCH header of partition 0, with no DAT. A decrypted image is filed in `library/roms/n3ds/` as `<name>.cci` (a `.3ds` is renamed, the bytes do not change) and nothing is overwritten. An encrypted image (Azahar opens only decrypted ones) or an invalid header goes to review with the reason, instead of "no DAT match". See [docs/inbox.md](docs/inbox.md).

## [0.2.0] - 2026-11-02

### Added

- Emulator settings layer. The hub keeps key-level layers (`settings/common.toml`, `settings/<device>.toml`) in a new two-way folder `wz-settings` that a device joins with the `settings` group, and the `steamos-emudeck` profile declares the settings files of eleven emulators (Eden, RetroArch, DuckStation, PCSX2, Dolphin, Azahar, melonDS, PPSSPP, Vita3K, xemu, Ryujinx). `warpzone settings capture` takes a setting changed in an emulator's own interface to the layers (`--seed` fills them from a console that is already configured), `warpzone settings apply` writes the layers into the emulators' files and `warpzone settings audit` reports the drift. Apply never writes while the emulator runs, never overwrites a change that was not captured (unless `--overwrite-local`), changes only the layered keys, backs up each file first and touches nothing when a layer is invalid. Logins never reach the hub. See [docs/settings.md](docs/settings.md).
- `provision device` installs an ES-DE startup script that runs `settings apply`, and turns on ES-DE's custom event scripts when ES-DE is closed. `warpzone doctor` checks the layers, the script and the last apply.

### Fixed

- Syncthing as a flatpak (SyncThingy) cannot see other apps' `~/.var/app/<app>` folders, so the RetroArch, Dolphin, PPSSPP, PrimeHack and Flycast save folders looked empty to it and synced nothing. `provision device` now adds the missing `flatpak override --user --filesystem=~/.var/app/<app>` for each of them (idempotent, reported in `--dry-run`) and asks for a Syncthing restart. `warpzone doctor` checks the overrides and prints the command for each missing one.
- The Syncthing unit that `warpzone doctor` suggests for the SyncThingy flatpak now has `ExecStop=/usr/bin/flatpak kill ...`. Without it `systemctl --user stop` leaves the flatpak process running and a restart loops in `activating (auto-restart)`. `doctor` warns about a unit in that state and shows the fix, and the unit is documented in `docs/emudeck.md`.
- `warpzone doctor` warns when Vita3K's active user is not `00`. The profile syncs the saves of user `00`, and a user created in Vita3K's window can get another id, which left its saves unsynced.
- Dreamcast: the `steamos-emudeck` profile now ignores `/bios/dc/vmu_save_*.bin` and `/bios/dc/dc_nvmem.bin` in the device library. RetroArch's Flycast core writes them there, so a receive-only console listed them as local changes and a revert would have erased them. `warpzone doctor` warns when the core option for per-game VMUs (`reicast_per_content_vmus`) is off, since only per-game VMUs end up in RetroArch's saves folder and sync. Run `provision device` again to apply the new ignore lines.

## [0.1.0] - 2026-10-28

First public release. warpzone keeps one game library on a home server and delivers it to every console through Syncthing, with saves that sync both ways.

### Added

- Hub and device provisioning (`provision hub`, `provision device`) with a per-device whitelist kept on the hub and edited only there. Library, songs and tools are receive-only on devices.
- Whitelist bootstrap on the hub and on devices, so a new folder never scans or pulls the whole library before the whitelists are in place. Whitelist edits take effect within 5 minutes (`rescan_seconds`).
- Two-way save folders for the emulators of the `steamos-emudeck` profile, pointed at the real emulator directories because Syncthing never follows the symlinks EmuDeck creates. Hub history is kept for 30 days.
- BIOS placements: keys and firmware (Eden, Azahar, Cemu) delivered into each emulator's own folder as receive-only folders with their own ignore lists.
- `warpzone prune` reports, and with `--apply` deletes, files a device no longer whitelists, only when the hub still has them unchanged and within a size cap.
- `warpzone bios` checks BIOS and firmware per system against names, sizes and hashes (no BIOS is shipped or downloaded), with local overrides in `bios.toml`.
- `warpzone inbox` identifies new discs and cartridges by content against Redump and No-Intro DATs, converts them (CHD, zip, ISO), verifies them with `chdman` and RetroAchievements hashes, and files them without overwriting anything.
- `warpzone inbox` files Nintendo Switch `.nsp` and `.nsz` games, updates and DLC by TitleID and version, named after titledb.
- `warpzone inbox` files arcade sets by choosing the emulator the set fits (FinalBurn Neo, MAME, MAME 2003-Plus, or Flycast for Naomi and Atomiswave) and writing the ES-DE per-game override with a backup.
- `warpzone inbox` files PS3, Xbox and Xbox 360 disc images by signature.
- `warpzone doctor` checks the tools, config, Syncthing, DATs and hub folder of a machine and prints the fix for each problem.
- `warpzone status`, `check` and `render-ignores` to inspect folder state, validate the config and preview a device's ignore lines. `provision` supports `--dry-run`.
