title: "Safety"
---

The rules `warpzone` follows so that a mistake on a console or in a command cannot damage the library.

- **Receive-only devices.** The library, songs and tools are receive-only on devices, so a delete or an edit on a console can never propagate to the hub.
- **Path changes are refused.** If a `wz-*` folder already exists in Syncthing with a different path than the config says, `warpzone` stops: changing a folder's path makes Syncthing see a mass delete. Remove the folder in Syncthing first (files stay on disk), then provision again. The exception is a save folder whose profile moved it (`previous_paths`) while its old directory is empty or all its files are already on the hub: provision removes and adds it by itself (with the hub paused in the console's Syncthing for that moment and resumed right after), since nothing on disk can be lost and no file leaves a folder Syncthing syncs. Never move files out of a folder Syncthing still syncs: it would announce them as deletions.
- **Additive for devices.** Devices are never removed from Syncthing. `provision hub` stops sharing a `wz-*` folder with a configured device that no longer subscribes to it; no file is deleted. Folders that are not prefixed `wz-` are never touched. Existing `wz-*` folders are patched only for the keys `warpzone` owns (label, path, type, devices, versioning, file watcher, and the rescan interval of whitelisted device folders). Everything else you tuned is left alone.
- **Pruning is report-first.** `warpzone prune` reports by default. `--apply` deletes only files Syncthing ignores and the hub still has (or that the library UI deleted from the hub on purpose, which the hub's record of deleted games proves), within a size cap ([Whitelists and pruning](/warpzone/setup/whitelists/#pruning-what-a-device-no-longer-whitelists)). A console that lists `library` also runs it from a timer, without the cap but never when it would delete more than half of what a folder holds ([Automatic pruning](/warpzone/setup/whitelists/#automatic-pruning)).
- **Dry run.** `provision` supports `--dry-run`: it reads state, prints the calls it would make (method, path, JSON body) and sends none.
- **Secrets.** API keys are never printed, logged or included in error messages, and are redacted from dry-run output.
- **Where it runs.** `provision device` talks to the local Syncthing on loopback (self-signed HTTPS is accepted only there) and reads the hub's API only to check that the whitelists exist before it changes anything. If the hub is unreachable it warns and carries on, because the bootstrap ignores keep it safe.
- **Deleting from the UI goes to a trash.** The library UI deletes only a whole game, only after showing everything it will move and getting your confirmation, and moves it (never deletes it) into `trash/` at the hub root, outside every Syncthing folder, where it can be restored for 7 days. It refuses while an inbox or a scrape runs and refuses an arcade set other sets need. Saves are never deleted. Moving files out of `library/` is what makes the consoles delete the game, which is the point here; a console's whitelist lines are removed only after it received the deletion, so no console keeps a stray copy ([Deleting a game](/warpzone/development/design/library-ui/#deleting-a-game)).
- **Inbox never overwrites.** `warpzone inbox` reports by default, only adds files, and sends anything it cannot place to review ([Adding games](/warpzone/setup/inbox/)).

## Snapshots on the hub

The hub is the authority, and `warpzone` keeps no versions of the library (saves get 30 days of staggered history; a game deleted from the UI stays 7 days in `trash/`). Turn on filesystem snapshots for the hub's games share (Btrfs on Synology, ZFS, or whatever your NAS offers). A bad edit or a deleted folder on the hub then costs one rollback instead of a re-download.
